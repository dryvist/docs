## Three tiers

The engine exposes three access tiers. Each is a distinct OpenBao identity with
its own policy, so the tier a caller holds is the whole privilege
boundary.

| Tier | Scope | Policy configuration | Gate |
| --- | --- | --- | --- |
| Read | All repositories of an account installation, read-only | A named read permission set that stores a read-only permission map | Ambient: reading is pre-authorized |
| Write | Exactly one named repository per request, at the App ceiling on that repo | The raw mint endpoint, with an OpenBao policy that requires and allowlists the repository parameter | Ambient for allowlisted repositories |
| Admin | An account installation's full ceiling across every repository | A named full-automation permission set | Human-only: an interactive, single-use grant per elevation |

Read and administrator tiers mint from named permission sets, whose stored scope the
request body cannot widen. The write tier is the one identity allowed to use the
raw mint endpoint. Its policy pins the request: the repository parameter is
required and drawn from a reviewed allowlist. The parameters that would name
a whole installation or an arbitrary permission map are denied. So a write
token carries write access to a single named repository, not an account.

Adding a repository to the write allowlist is a reviewed configuration change,
not something a caller can do at request time. GitHub still enforces the outer
ceiling underneath all three tiers: an installation token can never exceed what
the App installation itself holds.

### What the read tier can see

The read permission set is deliberately wider than "clone and read code." It
also carries read on security events and on dependency vulnerability alerts.
So code-scanning findings and dependency alerts are queryable under the
ambient read token, with no elevation and no claim required. Security triage
is a read-shaped activity. Requiring a write token for it would have pushed
routine triage onto the privileged path.

## Separation from AWS

The GitHub engine and the [AWS STS engine](/security/tools/openbao) are separate
logical engines inside one OpenBao security boundary:

| Boundary | AWS | GitHub |
| --- | --- | --- |
| Mount | `aws/` | `github/` |
| Root trust | AWS credential configured for the engine | GitHub App ID and private key |
| Output | STS credential lease | App installation-token lease |
| Authorization | OpenBao role plus AWS IAM | OpenBao permission-set path plus App installation |

They have separate mounts, configuration, policies, and leases. Normal API
access to one mount does not authorize access to the other. They still share the
OpenBao root and administrator control plane, Raft storage boundary, hosts, plugin
runtime, and outbound HTTPS. A compromise of that shared boundary can affect
both engines.

## What it replaces

| Old access path | New mechanism |
| --- | --- |
| Routine read of any account repository | Ambient read tier: a read-only permission set |
| Automation that writes to a repository | Per-repository write tier: one allowlisted repository per request |
| Access outside the App permission ceiling | Human-only, interactive break-glass administrator tier |

The service engine does not add a generic administrator-verb broker. Routine reads and
per-repository writes are available to the agent within the reviewed allowlist.
An installation-wide token, or a repository outside the allowlist, stays on a
human-only, interactive break-glass path under
[Golden law #3](/security/golden-laws#3-human-approval-gates-every-potentially-destructive-action).

## Residual risk, honestly

OpenBao becomes the path to the GitHub App private key. A caller that can use a
mint endpoint can mint tokens up to that tier's scope until its OpenBao access is
revoked. The controls are layered:

- The App installation ceiling.
- The tier's scope (a read-only map, or a single allowlisted repository).
- Path- and parameter-scoped OpenBao policy.
- One-hour GitHub expiry.
- Explicit lease revocation.
- OpenBao audit logs.

Per-repository write keeps a leaked write token's blast radius to one
repository. The installation-wide administrator tier stays human-gated precisely
because it is the broad one. That makes the shared OpenBao boundary the
target that matters.

The GitHub plugin is a third-party Apache-2.0 component. Its signed checksum
manifest, binary checksum, compatibility with the deployed OpenBao version, token
use, and revocation behavior were verified before the rollout was marked live.

## Environment variables

`gh` reads `GH_TOKEN` or `GITHUB_TOKEN` from the environment.
