Commits are the primary changelog; they get the same care as the code they describe.

The shape of every commit message and PR title across the org follows the rules below. Release
tooling (`release-please`) reads these to compute version bumps, so deviations from the convention
are not stylistic; they change what ships.

## Commit and PR subject lines

- **No emoji in commit messages, PR titles, PR descriptions, or release notes.** Emoji in READMEs and docs is allowed, minimally and purposefully, but never in machine-parsed subjects.
- **Conventional-commit prefixes** (`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`, `ci:`, `build:`, `perf:`, `style:`, `revert:`) for every commit subject and every PR title. No exceptions.
- **Scopes use only lowercase letters, digits, hyphens, and underscores.** Write `fix(github):`, not `fix(.github):`. A scope with `.`, `/`, or a capital letter fails the branch ruleset.
- **Squash subject.** The pull request title is the squash subject on the default branch. Promotions into
  `main` use a merge commit; see [Branch conventions](/conventions/branch-conventions#promotion).
- **`fix:`** for config tweaks, small improvements, incremental adjustments, dependency updates. Produces a patch bump.
- **`feat:`** for genuinely new capabilities, integrations, or significant behavioral changes. Produces a minor bump.
- **Major bumps are human-initiated only.** Edit `.release-please-manifest.json` manually.
  Automated major bumps (including from `BREAKING CHANGE:` footers) are blocked by the release
  workflow. Agents never write a `!:` subject or a `BREAKING CHANGE:` footer. Repos set release-please
  `versioning: always-bump-minor` so a breaking commit cannot cut a major.
  See [CI/CD policy](/infrastructure/cicd/policy) for the release flow.

## Trailers

Agent commits end with an `Assisted-by` trailer that names the tool and the model, in the form
`Assisted-by: <tool>:<model>`. Pull request policy requires this trailer on agent pull requests.
The review picks a reviewer from a different model family from the one named in the trailer.

## Enforcement

Two gates check the subject line. Message bodies and other trailers are free text.

- **Local.** A `commit-msg` hook rejects a bad subject before the commit exists. A global hook covers git 2.54 or later.
  Every repository dev shell also installs a pre-commit `commit-msg` hook, which works with any git version.
- **Server.** Rulesets check every pushed commit on every branch. Default branches accept only Conventional Commit subjects.
  Other branches also accept `Merge ...` subjects for git-flow promotions. A bad subject fails the push with `GH013`.


## Tone in PR descriptions and review

- **Tell hard truths directly.** Don't soften. Don't sandwich. Disagree when you disagree.
- **ALL CAPS from the requester means refocus immediately** on the previous direction. Treat a capitalized correction as the highest-priority signal in the conversation.
- PR descriptions state what the change does now; see [PR conventions](/conventions/pr-conventions) for the body format.

## Autonomy

- **Small fixes: just do it.** Commit when the task calls for it; do not wait for instruction on changes that are obviously scoped, obviously correct, and obviously safe.
- **Big architectural decisions: ask first.** Schema changes, public API shape, dependency adds, anything that changes the contract another repo depends on.
- **Major side quests: file a GitHub Issue and move on.** Side quests almost always grow; an Issue captures the context so the original task stays focused.
- **Always explain complex reasoning.** A two-line diff with five lines of justification is fine; an ambiguous diff with no rationale is not.
