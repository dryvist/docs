On a default-branch squash merge, the pull request title becomes the commit subject.

Pull requests are the unit of change that lands on the repo's integration branch: `develop` on
git-flow repos, `main` on trunk-flow repos. See [Branch conventions → Which model
applies](/conventions/branch-conventions#which-model-applies) to check which one a given repo
uses. The title and merge strategy determine what the changelog says.

## Title

- **Use the same [conventional-commit prefix](/conventions/commit-conventions) the squash commit
  uses.** `feat: …`, `fix: …`, `chore(scope): …`. The squash-merge takes the PR title as the
  commit subject verbatim; if the prefix is wrong, `release-please` computes the wrong version bump.
- **No emoji.** Same rule as commit subjects: machine-parsed surface, no decoration.
- **Under 70 characters.** Lengthy context belongs in the body, not the subject line that GitHub
  truncates in the merged-PR list.
- **Imperative mood**, present tense: "add netflow firewall rule," not "added" or "adding."
- **Scope is optional, lowercase, in parens** when used: `feat(api): rate-limit token refresh`.

## Body

Three sections, in this order:

1. **`## Summary`**: 1–3 bullets covering what the change does now. If the PR closes a Linear
   issue or GitHub issue, say so here (`Closes JAC-50`, `Fixes #127`).
2. **`## Test plan`**: bulleted markdown checklist. What CI runs automatically (`bun run build`,
   `pnpm test`, `tofu fmt -check`), and what you verified by hand (browser smoke test, reviewed Terrakube plan, anything CI cannot see). Tick the boxes as work completes.
3. **Optional: `## Security notes`**: when the change touches credentials, IAM scopes, network
   exposure, or anything else where the security review is non-obvious from the
   diff. Empty section = "I considered it and there is nothing to flag" (different from "I did not
   think about security").

## Lanes

One classifier decides the lane of each pull request from the pull request itself: its files,
size, labels, and author. It runs on the pull request and again in the queue.

| Lane | Who gets it | Before merge | After merge |
| :--- | :--- | :--- | :--- |
| tiny | 10 changed lines or fewer and every file low-risk. No label needed. | Fast checks. | Heavy checks and review. |
| land-first | The label `land-first` and no guarded path. | Fast checks. | Heavy checks and review. |
| normal | Everything else. | Fast checks, review verdict, heavy checks mapped to changed paths. | — |
| guarded | Secrets, secret-store policy, rulesets, and workflow files. Never tiny, never land-first. | Fast checks, review verdict, full suite. | — |
| bot | Pull requests from Renovate, from release-please, and automatic reverts (label `auto-revert`). | Checks mapped to changed files. No verdict. | — |

Low-risk files are docs and markdown, tests and fixtures, dashboards, and static content.
Instruction files (rules, prompts, skills, agent files) are never low-risk, even when they are
markdown. A pull request from a sandbox executor or from a fork always takes the normal or guarded
lane. A comment-only edit in a code file uses the `land-first` label.

## Life cycle

Open the pull request ready; drafts are not used. The platform arms native auto-merge on every
same-repository pull request that does not carry the label `human:review`.

### Hot repository

The pull request enters the merge queue when its checks pass. The queue merges it by squash.
Nobody merges by hand and nobody updates a pull request branch by hand: the queue builds every
entry on the newest default branch.

### Standard repository

Auto-merge merges it by squash. A standard repository does not require the branch to be up to
date.

Pull request control is event-driven. Fork pull requests are never armed automatically.

## Labels

- `land-first`: marks a pull request for the land-first lane.
- `preflight`: runs the heavy checks early on a hot repository's pull request.
- `checks:deferred`: added by the gate to tiny and land-first pull requests; heavy checks and
  review happen after merge.
- `auto-revert`: marks automatic revert pull requests.
- `human:review`: the hold label; see [Holds](#holds).

## Holds

`human:review` is the only hold. Agents and executors never add it.

## Pull request bots

One CI-fix agent (starts on a failed queue run or on a label; 2 attempts), one review responder
(starts on a CHANGES verdict), one conflict worker. They share one writer slot per pull request
and skip a pull request that is in the queue, because a push removes it from the queue.

## Merge strategy

Squash into the default branch by the queue or auto-merge. Promotions and hotfix pull requests into `main` use merge commits.

## Review

No person reviews before merge: the `AI Merge Gate` check, posted by the reviewer App with a model from a
different family than the author, is the review. See
[CI/CD policy](/infrastructure/cicd/policy#required-checks) for the required checks.

## Tone in the description and review thread

- **Tell hard truths directly.** Don't soften with "perhaps" or "maybe consider." Disagree
  explicitly when you disagree.
- **ALL CAPS from the requester means refocus immediately.** A capitalized correction is the
  highest-priority signal in the conversation; everything else pauses until that direction is
  followed.
- **Explain complex reasoning.** A two-line diff with five lines of justification is fine; an
  ambiguous diff with no rationale is not.
