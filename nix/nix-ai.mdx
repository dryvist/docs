> The whole AI toolkit, in one flake. `nix run` and go.

<RepoMeta language="Nix" status="active" lastActive="this week" repoUrl="https://github.com/JacobPEvans/nix-ai" />

`nix-ai` is the package and config layer for everything AI-coding-related. It packages command-line
tools that don't yet have first-party Nix derivations. It also pins MCP server versions and exports
overlays that the rest of the Nix stack consumes.

Host-specific provider wiring is intentionally outside `nix-ai`. If a tool needs
to point at a private local LLM gateway, package the tool here. Then keep the
endpoint configuration in the consuming workstation flake. That keeps
reusable packaging public and environment topology private.

## What it does

- Packages Claude Code, the Antigravity (`agy`) command-line tool, the GitHub Copilot command-line
  tool, Cribl and Splunk operator command-line tools, and assorted AI tooling
- Tracks the operator command-line tool sources through the flake lock, so consumers can gate their
  installation to workstation hosts
- Provides MLX module derivations for Apple Silicon
- Pins a catalog of MCP servers and exposes them as reusable Nix attributes;
  most of the catalog is on-demand, not always-on (see below)
- Exports an overlay so `nix-darwin` and `nix-home` can include AI tools without duplicating logic
- Includes a shell module (`devShells.default`) for a ready-made AI sandbox
- Adds the [`zcode-job` package](https://github.com/dryvist/nix-agent-sandbox/blob/main/nix/zcode-job-module.nix)
  to the Darwin Home Manager `PATH`; its connection configuration stays opt-in.

## Configuration surface

`nix-ai` ships as a reusable flake module with a single knob surface: `modules/maintainer-profile.nix`. This is the one file a consumer touches to adapt the stack:

- **Identity** fields (`user.fullName`, `user.trustedOrgs`) have maintainer defaults, so derived
  values (for example, the Claude auto-mode trusted-org list) stay internally consistent. Override
  them for your own identity.
- **Infrastructure** fields (`homelab.*`, `telemetry.*`, `trustedProjectDirs`) default to
  clean/off/empty, so the module evaluates to a neutral config with zero consumer input. No
  personal context ships in the flake.

Modules read `userConfig` via `_module.args`. Only `maintainer-profile.nix` imports it directly.

To override a value, set it in your own `nix-darwin` config through `extraSpecialArgs`. You can
also import the module and set its options.

The [nix-ai-open-harness Home Manager module](https://github.com/dryvist/nix-ai-open-harness/blob/main/flake.nix)
wraps nix-ai's OpenCode module. Its default value for `awesome-claude-skills`
uses `lib.mkDefault`, so a consumer's explicit module argument takes priority.

### Environment variables

The variable catalog (required vs optional, purpose) lives in `.env.example` at the repo root.

### Splunk MCP entry

The Splunk entry is one shared catalog item rendered for Claude, Codex, Qwen,
and the Antigravity command-line tool and IDE surfaces. Antigravity (`agy`) is the
Gemini-family harness; it is not a second Gemini MCP identity. Hermes uses the
same Splunk connection.


### On-demand MCP servers

MCP tool schemas are the largest addressable per-session token cost. So most
local servers stay out of the always-on profile: `apple-events`, `zammad`,
`fabric`, `grep`, `time`, and `token-meter` render to
`~/.claude/mcp-available/<name>.json` instead of loading at session start.
The always-on profile carries only what the gateway routes (`context7`,
`memory`) plus `vikunja`. The Codex command-line tool can explicitly attach
selected entries from the on-demand registry by setting
`programs.codex.onDemandMcpServers` to
names in `programs.aiMcp.onDemandEnabledServers`. The selected servers are
rendered into Codex's `config.toml`; remote servers can read their bearer key
from the named consumer environment variable at runtime. See the
[Codex option](https://github.com/dryvist/nix-ai/blob/develop/modules/codex/options.nix)
and [renderer](https://github.com/dryvist/nix-ai/blob/develop/modules/codex/settings.nix).

A repository attaches on-demand servers through its skill groups instead of listing
them by hand. `programs.agentSkills.groupMcpServers` maps a group to server names
(default `homelab` → `zammad`; `ai` → `fabric`, `grep`, `time`, `token-meter`). The
direnv linker merges those with any `AGENTS.md` `mcp-servers:` frontmatter. The result
goes into the managed part of an untracked `.mcp.json`. Ten rarely used Zammad tools stay denied by
bare-name permission rules so their schemas never reach context even when the server
attaches. The curated on-demand list is a config-level definition, so a consuming host
can append a server without losing the default set.

## Getting started

<Steps>
<Step title="Try a single tool">
`nix run "github:dryvist/nix-ai?ref=vN#claude-code" -- --help`, where `vN` is the current major tag. No clone needed.
</Step>
<Step title="Enter the sandbox shell">
`nix develop "github:dryvist/nix-ai?ref=vN"` drops you into a shell with every AI command-line tool on PATH.
</Step>
<Step title="Import into nix-darwin">
Add `nix-ai` as a flake input, then include `nix-ai.overlays.default` in your nixpkgs config. The README has the boilerplate.
</Step>
<Step title="Override the maintainer profile">
Set `userConfig.user.fullName` and any `homelab.*` / `telemetry.*` options in your own config to adapt the stack to your environment.
</Step>
</Steps>
