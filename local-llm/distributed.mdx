> Two Macs can cooperate; they cannot merge. The gain is capacity: serving a model too large for one machine, not making a model that already fits run faster.

MLX distributed can shard one model across separate Apple Silicon memory
pools. The machines exchange activations over a Thunderbolt link using TCP or
the RDMA-based JACCL backend. The link does not turn their unified memory into
one pool.

The lifecycle for this fleet is operator-triggered. Cable connection alone does not join or detach the cluster. The detailed procedure remains in the private runbook.


## The memory trade-off

There is no combined unified-memory pool. Each Mac keeps its own memory, and
the model is divided across the pair. Sharding lets the pair run a model that
exceeds one Mac's capacity. Each rank still needs space for its shard, KV cache,
and runtime overhead.

Measure GPU-wired residency with the platform's wired-memory accounting, not a process's RSS. Unified-memory allocations may not appear in a process's RSS.

## Two workers or one sharded model?

```mermaid
flowchart TB
  Q{Does the model fit in one Mac?}
  Two[Run independent workers<br/>split requests for throughput]
  Shard[Shard one model across both<br/>for capacity]
  Q -->|yes| Two
  Q -->|no| Shard
```

- **If it fits on one Mac,** run an independent worker on each and divide requests between them.
- **If it does not fit,** shard one model across the pair. This trades link traffic and coordination for additional model capacity.

Which parallelism mode a model supports depends on its architecture. Pipeline
and tensor parallelism have different sharding behavior and sizing needs.
Check the model's declared capability before choosing a mode.
