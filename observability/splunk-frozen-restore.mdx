## When to use this

You need data that has aged out of Splunk. Either an index reached its
retention window, or a volume cap evicted the oldest buckets to make room.

This is not a search. Archived data is offline, and bringing it back is a
deliberate operation measured in minutes.

## The default that makes this necessary

Splunk **deletes** a bucket when it ages out unless native freezing catches it.
Configure <code>coldToFrozenDir</code> to send frozen buckets to the
bulk-storage volume before a retention window or volume cap can bind. The
existing replication and offsite chain protects that volume. Custom archive and
restore scripts are being removed in favour of native
<code>coldToFrozenDir</code>.

<Warning>
**Enforcing retention and losing data is the same action without an archive.**

Tempted to lower a retention setting or a volume cap to reclaim space?
Confirm archiving is enabled **first**. Otherwise the space is reclaimed by
permanently deleting whatever was oldest.
</Warning>

## What the archive is, and is not

| | |
| --- | --- |
| **Is** | A frozen bucket on bulk storage, protected by the existing replication and offsite chain. |
| **Is not** | Searchable. Nothing queries it in place. |
| **Is not** | Federated Search for Amazon S3 (see below). |

### Why not just search it where it sits

Federated Search for Amazon S3 doesn't apply to a typical self-managed
deployment, on three independent grounds:

- it's a Splunk Cloud feature, unavailable for Splunk Enterprise
- it's unsupported on single-instance deployments
- it requires an AWS Glue Data Catalog, which has no equivalent outside AWS

It also searches raw files rather than Splunk buckets, so it wouldn't read
archived index data even if the rest applied.

SmartStore is the only option that keeps aged data directly searchable. It
sits outside the supported topology for an on-premises indexer pointed at a
remote object store. It also removes the cold-bucket state entirely, and it
still requires days of local cache to warm. Treat it as a separate
architectural decision, not a drop-in fix for this workflow.

## Restoring a bucket

<Steps>
<Step title="Find the bucket">
Find the full bucket directory for the index. Bucket
names encode their time range. If the bucket is already archived offsite,
copy it back from that archive first.
</Step>
<Step title="Copy the bucket">
Copy the complete bucket directory, including all its
files. Do not copy only raw data files.
</Step>
<Step title="Put it in thaweddb">
Copy it into
<code>$SPLUNK_DB/&lt;index&gt;/thaweddb</code>. Bucket IDs must not collide
with another directory already in <code>thaweddb</code>. Choose a
non-conflicting directory rather than overwriting one.
</Step>
<Step title="Rebuild the index">
Run:
<code>splunk rebuild &lt;bucket_path&gt; &lt;index_name&gt;</code>

Splunk documents this command in its
[Restore archived indexed data guide](https://help.splunk.com/en/splunk-enterprise/administer/manage-indexers-and-indexer-clusters/10.6/back-up-and-archive-your-indexes/restore-archived-indexed-data).
</Step>
<Step title="Restart or wait for pickup">
Restart the indexer or let it pick up the
bucket, then confirm the restored time range is searchable. Do not infer
success from files being on disk.
</Step>
</Steps>

## After restoring

<Warning>
**Thawed data never ages out on its own.** Data in <code>thaweddb</code> is
exempt from retention. Delete the thawed bucket from that directory when it is
no longer needed.
</Warning>
