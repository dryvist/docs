This page is the IaC-flavored cut. For the broader posture (every tool, every tier), see [Security overview](/security/overview) and the dedicated [SOPS tool page](/security/tools/sops).

## When SOPS is the right answer

SOPS-encrypted files live inside a single repo. The
question to ask before reaching for it is **blast radius**. Consider an AI agent, a hostile
reviewer, or a careless paste into a Slack channel. If any of them decrypted this file and posted
it publicly, what would actually break?

- **If the answer is "nothing meaningful" AND the value is used by only this one repo** (a per-host
  Ansible variable that names an internal interface, structured config the same repo consumes), SOPS
  is a fine fit. But do **not** default to SOPS: the moment another service, a human, or an agent
  might need the value, it belongs in OpenBao (T2), not a repo-local file. SOPS is the exception,
  not the reach-for-first tool.
- **If the answer is "an attacker can now hit AWS / Doppler / a third-party SaaS"** (API tokens,
  OAuth keys, HEC tokens, license keys, anything an external service treats as a bearer credential),
  that value does **not** belong in SOPS. It goes in Doppler.
- **If the answer is "an attacker can now move laterally inside the homelab"** (the master Proxmox
  root password, an iDRAC administrator credential, anything that grants control-plane access if exposed),
  it goes in Keychain, not committed at all.

The mental model is "would a one-time public leak of this exact string be a paper cut, or would it be an incident?" SOPS is for paper cuts.

## The four-tier split

| Tier | Holds | Mechanism |
| --- | --- | --- |
| **Runtime store (default)** | App/DB passwords, administrator passwords, service tokens | **OpenBao** |
| Encrypted-at-rest in git (single-repo exception) | Values used by exactly one repo that are neither mission-critical nor public-service creds: per-host vars, structured config the same repo consumes | SOPS + age |
| Cloud/SaaS | External API tokens and license keys | Doppler |
| Local-only material (control-plane / never-on-disk) | macOS-side AI tool secrets, master/administrator credentials, anything that must never reach a shell history | macOS Keychain |

## Cross-repo: SOPS is for one repo, not many

A single secret should have exactly one source of truth. SOPS works cleanly when the value is
consumed only by the repo it's committed in.

When two repos both need the same value, do **not** SOPS-encrypt it twice. That's a DRY violation.
The two copies drift the first time one repo rotates without notifying the other, and the only
signal you get is a production failure. The decision tree:

- **Repo A is fully dependent on Repo B** (B publishes a value, A consumes it, A never rewrites it)
  → Repo B owns the value.
- **Repos A and B can both update the value independently** → SOPS in neither.
- **The value is genuinely local to one repo's CI/test/bootstrap** → SOPS in that one repo. No cross-repo concern exists.

## How it shows up in Ansible repos

[`ansible-proxmox`](/infrastructure/repos/ansible-proxmox),
[`ansible-proxmox-apps`](/infrastructure/repos/ansible-proxmox-apps), and
[`ansible-splunk`](/observability/repos/ansible-splunk) all follow the same pattern:

```yaml
# secrets.sops.yml.example — committed
NAS_HOMEASSISTANT_SMB_PASSWORD: change-me
```

```bash
cp secrets.sops.yml.example secrets.sops.yml
sops --encrypt --in-place secrets.sops.yml   # encrypts in place
git add secrets.sops.yml                     # safe: values are ciphertext now
```

## The `.sops.yaml` configuration

Each repo declares which paths to encrypt with which keys at the repo root:

```yaml
creation_rules:
  - path_regex: \.sops\.json$
    age: >-
      age1aaaa... # public age recipient
```

Only the public half of the age key appears here. The example shown is a placeholder.

## What you must never commit

Per the secrets policy, never commit real IPv4 addresses, internal hostnames, domain names,
AWS account IDs, SSH keys, or user-specific paths. Use placeholders or variables for anything
tied to one user; every committed value should work for any person who clones the repo right now.
The committed scrubbed-value table is `192.168.0.*`, `example.com`, `example.local`,
`your-token-here`, generic role-based usernames.

## Rotating the age key

Recipient rotation is the same across every repo that uses SOPS:

<Steps>
<Step title="Add the new public recipient to every .sops.yaml">
Keep the old recipient until cutover so neither party loses access mid-rotation.
</Step>
<Step title="Re-encrypt every SOPS file with both recipients">
`sops updatekeys .sops.json` per file. The encrypted file changes; the plaintext doesn't.
</Step>
<Step title="Remove the old recipient">
Re-run `sops updatekeys` once more. Now only the new key can decrypt.
</Step>
</Steps>
