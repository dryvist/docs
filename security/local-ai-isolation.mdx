> Four layers of isolation. Each layer is sufficient on its own. Together, they make leakage structurally impossible.

This page is the proof, not just the claim. AI tools running on this workstation cannot read the
values behind the locked keychain. They cannot obtain a GitHub write credential without taking a
visible lease, and they cannot read the file paths where keys live at rest.

## Layer 1: scoped credential tiers

| Tier | What it grants | Gate | AI can reach it? |
| --- | --- | --- | --- |
| Read | Read-only across the account installation | Ambient: pre-authorized | Yes, freely |
| Write | Exactly one named repository, per request | A claim that takes an exclusive lease on that repository | Yes, but only one repository at a time, and visibly |
| Admin | The installation's full ceiling | Human-only, interactive, single-use grant | No |

## Layer 2: human-only keychain

There is no AI-readable keychain tier. The keychain holds human-only break-glass material in a locked database. The detail is in [macOS Keychain](/security/tools/macos-keychain).
The boundary that matters here is that an AI subprocess cannot satisfy the unlock
prompt. There is no unlocked database holding a credential it could use
instead.

## Layer 3: explicit allow / deny lists

The Claude Code permission system bakes a deny list into the build. Even if the previous layers were bypassed, the harness refuses the file paths that would yield secret material.

| Allow (read-only inspection) | Deny (Read / Edit / Write blocked) |
| --- | --- |
| `security find-generic-password` (lookup metadata) | `**/.env*` |
| `security list-keychains` | `**/secrets/**` |
| `security show-keychain-info` | `~/.gnupg/**` |
| | `~/.ssh/id_*` |

The allow list lets the AI inspect *metadata*, such as whether a keychain entry with a given service name exists, without ever returning the value.

## Layer 4: scoped unattended convergence

The interactive human account has no password-less escalation. Every `sudo` it
runs is biometrically gated, convergence included. Unattended convergence runs
instead under a dedicated automation account whose grant covers one exact
declarative command and nothing else. It applies store paths that were already
built, with no ad-hoc shell and no other read access. Which harnesses run under
that account is set out in
[harness trust tiers](/autonomous-agents/harness-trust-tiers).

## What AI can and cannot do

| Capability | AI tool | Why |
| --- | --- | --- |
| Obtain a read-only GitHub credential | ✅ | Ambient read tier; read-only by construction |
| Obtain GitHub write on one named repository | ✅ (one at a time) | Requires an exclusive, recorded, self-expiring lease |
| Obtain GitHub write across an account | ❌ | Repository parameter is pinned server-side per request |
| Obtain an installation-wide administrator credential | ❌ | Human-only interactive single-use grant |
| Recover a GitHub token from disk | ❌ | No token is ever written to disk |
| Read a value from the human-only keychain | ❌ | GUI unlock prompt; AI cannot respond |
| Modify keychain entries | ❌ | `security add-generic-password` not in allow list |
| Read `.env*` files | ❌ | Path glob denied |
| Read `~/.ssh/id_*` private keys | ❌ | Path glob denied |
| Read GPG keys | ❌ | `~/.gnupg/**` denied |
| Run `sudo` outside `darwin-rebuild` | ❌ | sudoers entry is path-restricted |
